## Automatic-policy profile (unrun)

Select workflow input `profile=automatic-profile` only after parent review; the default remains `one-chat`. The controller keeps the cache enabled and uses actual fake RPCs, approved fake commands, pane closures, and close acknowledgements. It samples 0/128/200/400 workload completions. Each checkpoint reports loaded known-workload canonical bytes and separately visible, draft and pending-approval sentinel bytes; actual eligibility remains null. At 200/400 a released workload body is restored through the public exact-restore path, then the controller requires an automatic workload release while the visible sentinel stays mounted and loaded at both observations; 0/128 record that this pressure check was not exercised. Visibility is checkpoint-only, not continuous across navigation. The pending approval stays active when ordinary navigation replaces its main view; the controller checks at zero and after each workload completion that it is unmounted, loaded, in progress, still awaiting approval, and has never received a close request. The draft sentinel is checked alongside it. A missing receipt, release, close acknowledgement, expected synthetic output, persistent sentinel, observed pressure, quiescence or cleanup is a failure, not omitted data. This unrun controller has not demonstrated that those public flows complete reliably under 400 conversations.

Heap and backing storage are sampled after renderer GC and kept separate from canonical body and metadata scalars. The canonical algorithm is hash-pinned to the production source; scalar conversion returns no bodies. No heap plateau or eligible-budget proof follows from one profile. Two-window and missed-event lifecycle behavior remain separate unverified tests. The retained app-log size is zero: child output is drained and discarded. Parent retrieval of workflow logs remains separately bounded. Keep the existing workflow deadline; a timeout is a failed observation, not evidence to enlarge it.

The fixed-candidate diagnostic records an allowlisted error code and, on any checkpoint failure, a separate scalar end-state and explicit checkpoint number. At checkpoints and on any failure when CDP remains available it records counts, nulls, rejections, maximum and total settled duration, active count, oldest tracked age and a workload ordinal for only the two cache-proof RPC methods. `-1` means the ordinal is unknown. In-flight detail is bounded to 512 entries per method; overflow is flagged and oldest age is unknown while overflow is active. Observing promises and reading scalars adds instrumentation overhead; it does not change the workload, deadlines or assertions.
