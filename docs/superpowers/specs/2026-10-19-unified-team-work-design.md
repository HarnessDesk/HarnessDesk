# Unified Team work and discoverable Flow creation

The owner asked to reduce the fragmented Overview, Run, Flow and Timeline navigation, reviewed a combined work-page draft, and requested continued implementation. The later Flow-creation screenshots are a follow-up after this consolidation.

## Team destination

The primary destinations are Work, Tasks and Chat. Work is the default when opening or starting a Team. Its first main content is the frozen Flow of the selected execution, followed by recent recorded activity. History expands in place below it. A plain Team without a Flow keeps its useful overview without an invented graph.

The owner further clarified that approvals, questions and replies should behave like an individual conversation. Their actual answer controls therefore remain in Chat or the corresponding conversation, rather than being duplicated above the Flow. Work has one concise pending-request hint with a direct Chat door; Chat carries the meaningful request count. Human Flow decisions stay visible on their nodes and retain the actual task/decision door.

Run identifies an execution, rather than a competing primary page. Existing history, selected execution, receipt, check retry, wrap, stopping and conversation navigation remain available through secondary controls with truthful states. Old persisted overview/run frame requests resolve to Work; old explicit requests continue to reveal their requested recorded step or activity. Other consumers of RunWorkspace retain their existing presentation unless they opt into the unified composition.

Tasks groups the existing board and findings ledger. A local choice selects their existing surfaces; findings keep their filters, publication state, errors and actions. Chat retains its existing thread and side-by-side behavior. The change does not create new host authority or alter policy execution.

## Visual composition

Graph, pending-request hint and activity share the same content edges. The graph has a bounded readable height and participates in the page scroll; it does not consume a full-screen canvas before activity becomes reachable. Role cards share icon/title baselines, dimensions and spacing. Marks are plain canonical glyphs; color identifies state rather than decorating every agent. Recent activity is visible before expansion. Only meaningful nonzero counts are shown; Work has no generic attention badge.

## Follow-up: Flow creation

The existing entry is Flows → New Flow. A new editor currently presents its seed policy name as “Your own shape”, splits the toolbar into floating groups and fills the inspector with large folded cards. The follow-up will make the creation state and back route explicit, put Save and Start in the same clear action sequence, and simplify the inspector using canonical design patterns. Required edits must be visible without an additional Edit step disclosure. Empty optional groups should not occupy oversized cards.

Policy parsing, validation, stale-preview checks, required inputs, save conflict handling and source identity remain unchanged. Starting an unsaved policy must still use the existing Team launch path and preserve its source snapshot. Save must never silently grant overwrite permission. Built-in and read-only sources keep their existing restrictions.

## Verification

Behavioral tests cover legacy navigation, plain and recorded Teams, current/historical execution identity, attention actions, inline activity expansion and Tasks findings access. Real-surface walkthroughs inspect both themes and narrow/wide geometry using the isolated fake-agent desk. Creation walkthroughs follow the actual entry, add/edit a step, save and open the Team launch configuration. Public frames contain fixture identities only. Passing focused checks do not stand in for unexecuted browser or native suites.

## Conversation hierarchy and compact records

The owner's later screenshots reject both the oversized record rails and the crowded approval/composer stack. Right rails use one compact fact grid per subject, bounded names and paths with full accessible values, and disclosures for exact technical records. Empty optional sections do not become large cards. Held permission and merely requested permission remain distinct; an unknown cost never becomes zero. Recorded comparison candidates, revisions, changes, publication, retry, abandon and review actions stay available.

Team approvals are requests in the scrolling conversation, with a compact real Agent identity and a clearly separated conversation link. All response choices remain in the card's normal flow and wrap within its width. The composer stays mounted below the stream: pending requests must neither erase its draft nor clip its controls. The same approval is read and answered through the existing store record in the Team and originating Agent session. The Chat tab carries a count and a subtle theme attention mark, respecting reduced motion. Repeated approval and working essays do not form another grey card above the composer; message queue consequences are concise and truthful for the actual recipients.

Conversation messages have a clear sender, readable body and independent timestamp. System activity has lower emphasis and does not repeat a full task sentence for every created card. Adjacent Flow additions may be combined only when the recorded execution round proves their shared origin. Card references still open the exact recorded task; message order, host state and original records are preserved. Human Flow actions open the exact existing answer surface directly from Work rather than sending the person to find the card again.
