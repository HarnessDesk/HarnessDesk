# Library measurement harness

This is a manual, macOS-only measurement tool and never runs in CI. Discovery measures installed-build help and version output, plus sign-in-free catalogue observations: Codex `app-server` `skills/list` and signed-out ACP `initialize`/`session/new`. ACP command updates are recorded only as commands; they never count as skills. A failed ACP `session/new` records the asked observation “no session while signed out,” while skill catalogue availability stays `unknown`. Discovery sends no model prompts and uses no sign-in.

Run the exact entry point after building the generated install metadata:

```sh
pnpm build:node && node script/measure/library.mjs --all
```

Measure just one agent with `--agent <id>`. Without `--ask` this performs exactly that agent's discovery. To send fixed model questions in one session, explicitly select one agent:

```sh
node script/measure/library.mjs --agent gemini --ask --env GEMINI_API_KEY
node script/measure/library.mjs --agent claude-code --ask
```

`--all --ask` is refused. An absent agent records `binary not installed` and exits 0. Every installed agent's ask run requires a successful preflight of its selected profile in this process; a forged flag or changed profile cannot authorize a launch.

`--env <NAME>` admits one caller environment variable only when the selected registry entry declares it as a sign-in secret (`GEMINI_API_KEY` for Gemini). An undeclared name is refused before discovery. A missing value records `could-not-ask: key not provided`. Discovery never receives the key. The key is passed only in the probe child's environment; the harness never puts it in arguments, prompts, files or logs, nor echoes it. Raw protocol responses stay inside the isolated driver, whose stderr is discarded; only exact fixture matches leave it for capture or persistence, plus the prompt-activity counts described below, which are integers under a fixed list of names and never a word the agent said. Results say `auth: environment key`, without the name or value.

The harness makes a fresh fixture per agent under `/tmp/hd-measure-*`: isolated synthetic home and repository, user/project/duplicate/invalid/oversized skills, rule sentinels, MCP configs, and a local fixture MCP peer. Child processes receive only the sanitized environment, fixture cwd and homes, fixture `TMPDIR`, and the selected CLI arguments. The fixture and captures are removed after its result is written.

A fixture that cannot be removed does not undo a result that is already written and printed. The removal retries up to five times, with a growing pause that starts at 200 ms, for the errors Node treats as transient (`EBUSY`, `EMFILE`, `ENFILE`, `ENOTEMPTY`, `EPERM`). A failure that survives is reported on its own stderr line, `cleanup incomplete: hd-measure-<id> was kept (<errno name>)`, which carries only the folder's own name and the error's errno name (`unknown` when it has none, never a message or a path), and the run exits 3. Exit 1 and `measurement refused: invalid arguments or unavailable isolation` stay what they were, a refusal; a refusal that is raised while a removal also fails still prints the cleanup line first. The harness removes only the folder it made, so `/tmp/hd-measure-*` folders left by earlier runs are for their owner to remove. The cause found in such leftovers was an agent helper still shutting down inside the fixture (a state file and a log were written while the removal ran; nothing was read-only or flagged): helpers share the agent's process group and can outlive the process the driver spawned, so the folder was listed, a helper added to it, and removing the directory then failed. Every driver now stops the agent's whole process group before it returns: SIGTERM, a grace period (1 s in the model driver, 5 s in the discovery drivers), SIGKILL for whatever is left, then a wait until the group is empty.

Before launching a probe, `sandbox-exec` preflight checks the exact profile. The strict profile starts with `(allow default)`, denies file reads and writes under `/Users` and `/Volumes`, then denies all writes before allowing writes only in the fixture roots, `/dev/null`, and `/dev/tty*`. Reads are allowed for fixture roots and the resolved Node and agent install directories (Cursor's own `versions/<version>` directory excepted: it is copied into the fixture, below); final denials cover each credential root and known-agent home so those cannot inherit an install-directory allowance. Strict mode also denies the real home Keychains directory and the `securityd` and `SecurityServer` lookups. Canary checks prove an unrelated read under a synthetic home, a credential read inside an allowed install directory, and an outside-fixture write fail; fixture reads and writes, an allowed install read, and spawning `/usr/bin/true` succeed. A direct file read of a disposable fixture keychain succeeds only in the keychain-read-only control.

Discovery runs under strict isolation for every agent. Only `--agent <id> --ask` for Claude Code (`claude-code`), Cursor (`cursor`) and Grok Build (`grok-build`) selects `keychain-read-only`; every other path stays strict. The exception allows reads under the real home’s keychain directory and **direct file writes to the keychain directory are denied**. It allows Mach lookups to `com.apple.securityd` and `com.apple.SecurityServer`: **Keychain Services calls through these allowed security services are not constrained**, including adding or updating the agent's own item. **Network access is unrestricted** in both profiles, so even a vendor CLI's discovery may reach the network. This change adds no sandbox rule.

Ask results record the actual `isolation` and `auth`. `owner subscription sign-in` is recorded only for an exception ask run that sent a prompt without an environment key; refusals before prompting and strict runs without a key say `no sign-in used`. Discovery keeps its existing result format.

Install discovery keeps absent candidates, unreadable versions, and unsafe-to-isolate install roots separate. It resolves symlinks before selecting a narrowly scoped install directory; a package or `versions/<version>` directory inside the current agent home can be allowed, but the whole config home cannot. Cursor's own `versions/<version>` directory is the exception: it is copied into the fixture and run from there instead (below). An install directory that is a whole home or a whole volume is refused. An install directory under another account’s home or on an external volume is refused. Node-based agents also get the resolved Node install prefix, held to the same rule; the harness refuses to start when it is not a safe read root. Unsafe or inseparable roots remain `could-not-ask` with a path class in the reason; no real path is persisted.

Cursor's launcher cannot run in place under the approved profile, so it runs from a copy. Measured 2026-10-03 against Cursor 2026.10.01-e373342: install discovery found the launcher and allowed its `versions/<version>` directory, yet `cursor-agent --version` could not run and the version stayed `unknown`. The launcher is a shell script under `~/.local/share/cursor-agent/versions/<version>/`, and `.local/share` is one of the credential roots whose final denial overrides the install-directory allowance, so the shell could not open the script (`Operation not permitted`). Removing only that denial was not enough on a real home: the script resolves its own location with `realpath "$0"`, which reads the metadata of every directory above it, and the blanket denial under `/Users` refuses those reads. Running it in place would have taken two changes to the approved profile, and neither is made: the profile text is pinned by test, and a test records that the same layout runs when it sits outside a credential root and is refused by that one denial when it does not. Of the three ways forward the owner chose the one that changes no rule, a copy staged into the fixture as the bridges are. What had been fixed before is the version itself: Cursor's calendar-and-commit version used to normalize to `unknown` even when it was read.

What is copied. When the launcher the install search resolved is Cursor's own `cursor-agent`, directly inside a folder that sits directly inside a `versions` folder, that one folder is copied into the fixture, to `agent-install/<n>/<version>/`, and every launch of Cursor is of the copy: discovery's `--version` and `--help`, and the executable the ask path hands the bridge. Nothing else is read for it: not the `versions` folder, not an older version beside it, not anything else under `.local/share`, no credential root. The folder is the vendor's own bundle, runtime and helper binaries, not a store of credentials. It must hold the launcher, a `node` runtime and an `index.js` bundle, or nothing is copied. The folder is judged whole before anything is written. A link is recreated and never followed, and a link whose spelling or whose real end points outside the folder refuses the copy (the real end is the operating system's, which follows a link before it applies a `..` after it, where Node's `realpathSync` folds the string and can say "inside"). So does anything that is not a file, a folder or a link: a named pipe, for one, would block a copy forever. A refused copy is never replaced by running the install in place: the result is `could-not-ask: cannot isolate`. File modes are kept. A folder keeps its mode too, except that its owner always keeps write access, so the fixture can always be removed; setuid bits, extended attributes and timestamps are not copied. The copy is made once per folder, however many paths lead to it, never over a copy already there, and only after the sandbox preflight has passed, so a machine that cannot isolate never pays for it. Any other agent, and Cursor's launcher when it is not in a `versions/<version>` folder (a Homebrew cask copy, say), keeps the in-place launch it always had, with its folder allowed as before.

What is persisted. A result for a run that launched a copy carries `stagedInstall`, beside `isolation` and `auth`: `{ "bytes", "files", "milliseconds" }`, the copy's own size, the number of files in it and the time the copy took, as whole numbers and nothing else about it. No path or file name is kept, and the version is the one already recorded. The harness measures them itself, so nothing an agent says can reach them. Result validation admits exactly those three names, as non-negative whole numbers, and only for an agent that is staged. They are not facts about what an agent loads, so they have no cell in the tier table, and the fact mapping and its committed records keep the same keys. A run that launched nothing from a copy records none. Measured on 2026-10-04 on one Mac, Cursor 2026.10.01-e373342 was 451 files and 619,056,524 bytes (about 590 MiB) and copied in 707 ms, inside a whole discovery run of about five seconds; the time is the disk's.

Why no rule changed. The copy sits inside the fixture, which the strict profile already allows to read and write, and `realpath "$0"` then reads only the fixture's own ancestors, `/tmp` among them, which no rule denies. So `sandboxProfileText` is the same text, pinned by its hash test, and the profile for a staged run, strict for discovery and `keychain-read-only` for an ask run, has no read allowance for the staged install's folder at all (the folder of any other candidate run in place is allowed as before). The copy goes with the fixture, through the same removal and the same `cleanup incomplete` line as everything else in it.

Claude Code and Cursor resolve the bridges shipped with HarnessDesk, just as `AgentRegistry` expands their app templates: Node runs `packages/claude-acp/dist/src/main.js` or `packages/cursor-acp/dist/src/main.js`. The selected CLI path goes only into the bridge's executable environment variable, and Claude's nested-session marker is cleared. Resolution reads the built files and installs nothing; a bridge absent from this build records `could-not-ask: bridge not installed`. Restore the repository dependencies with `pnpm install --frozen-lockfile`, then run `pnpm build:node` to build these packages. No global bridge install or registry download is required.

Node's normal import loader reads ancestor metadata while resolving symlinks; the strict home denial refuses that access even when the package itself is a safe read root. The harness therefore stages copies of the resolved bridge and its already-installed runtime dependencies (including peers) inside the disposable fixture and runs the copied entry. Each canonical source package must pass `installRootIsSafe`. At most 500 distinct packages are copied, dependency links point to the staged copies, and the originals are only read. Missing required dependencies record `bridge not installed`; an unsafe source root records `cannot isolate: bridge install directory unsafe`. Staging adds no sandbox rule, no bridge read allowance outside the fixture, no HOME redirection and no install step.

Ask RPC refusals record a fixed `reason`: `sign-in not reachable under the approved profile`, `network refused`, `quota`, or `unknown`. `facts.requestFailure` contains only the stage (`initialize`, `session-new` or `prompt`) and a fixed JSON-RPC error class. ACP's authentication-required code is distinguished from a generic server error; vendor messages and error data are reduced inside the isolated driver and never leave it. Missing bridges, process launch failures and unanswered requests retain separate reasons. A pre-prompt refusal still records `auth: no sign-in used`.

Measured 2026-10-03 against Grok Build 1.0.30: under the unchanged `keychain-read-only` profile, `initialize` answered and `session/new` refused with ACP error code -32000 (`authentication-required`). The reduced result was `could-not-ask: sign-in not reachable under the approved profile`, stage `session-new`, with zero prompts. The diagnostic used an isolated synthetic home and sent no sign-in request. Its raw error text was discarded; changing sign-in access remains the owner's decision.

While a prompt is outstanding, an ACP agent may make requests of its client. The driver answers them without allowing or running anything for the agent. A `session/request_permission` request is refused the way ACP specifies, with an outcome and not an error: the request's own `reject_once` option is selected when the agent offers one, and the outcome is `cancelled` when it does not. `allow_once`, `allow_always` and `reject_always` are never selected (`reject_always` would write a standing decision into the agent's own permission memory), no tool call proceeds, and the agent ends its turn by itself. Every other request, `fs/*`, `terminal/*` and anything unknown, still gets JSON-RPC `-32601` method-not-found: the client's `initialize` advertises neither the `fs` nor the `terminal` capability, so an agent that sends one has left the protocol and has no outcome to wait for. This targets the Gemini 0.62.0 prompt timeout, where the harness answered a permission request with `-32601` while ACP expects an outcome and the agent waited for it until the prompt's deadline. It is proven with a scripted agent that waits exactly so; no real agent was prompted, so Gemini itself is still to be measured again. The Codex app-server driver is unchanged and still answers every request it receives with `-32601`. No sandbox profile changed.

A prompt that fails or times out now says what the agent was doing. When an ACP ask run ends `could-not-ask` after a prompt was sent, `facts.promptActivity` holds how many messages of each kind the agent sent during the latest prompt, each from 0 to 500 (a flood is capped): its `session/update` kinds under their ACP names (`agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update`, `plan` and the others in `ACP_ACTIVITY`), and its requests of the client under one fixed name per method (`session_request_permission`, `fs_read_text_file`, `terminal_create` and the others in `ACP_ACTIVITY`). Anything outside those lists, including an update kind the harness does not know, counts as `other`. The window opens when the prompt is sent, so a notification the agent sends for its session's setup that arrives after that, typically one `available_commands_update` just after `session/new`, is counted too. Only the names and the counts are kept: no text, identifier, path, tool name or title, and nothing the agent said selects a key, because the count is made inside the isolated driver and the persisted keys are checked again against the same list. A count under any other name is refused by result validation, and the run keeps its reason and loses the facts. Nothing is recorded for a Codex run or for a prompt that succeeds.

Discovery interfaces and scope:

- Codex: `codex app-server`; query `skills/list`, config and MCP status without sending a model prompt.
- Gemini CLI, OpenClaw, OpenCode, Cline, Hermes, CodeBuddy Code, Kimi, Pi ACP, GitHub Copilot CLI, Antigravity, DeepSeek, and Devin: the configured ACP bridge or agent command; send only `initialize` and `session/new`, never a prompt. Claude Code, Cursor, and Grok Build receive version/help discovery only; no ACP session or model prompt is sent.
- All builds: capture `--help` and the declared version arguments in the fixture, compare the parsed version with install discovery, and persist only the normalized version. That is either dotted numbers with an optional known prerelease label (`1.2.3`, `0.1.7-rc.2`) or Cursor's own scheme, a calendar date and a seven-character lowercase commit (`2026.09.28-64d2043`); anything else normalizes to `unknown`. Absent, unreadable, unsafe, and version-changed candidates remain distinct.

Raw answers are reduced to fixture-derived sentinel tokens. Structured model facts accept only fixed enums, booleans, integer counts from 0 to 500, fixture tokens, and concrete relative skill-root paths. Discovery retains its numeric protocol error codes. Vendor output, account identifiers, emails, tokens, secrets and absolute machine paths are never persisted or printed. A failed privacy validation becomes `could-not-ask`.

Ask runs use ACP `session/prompt` or Codex `turn/start`, with one session/thread per fixture. The harness counts requests at the protocol send: at most three prompts, including failures, and a fourth is refused. No user or fixture text enters a prompt, and no full sentinel token appears in one. The first fixed question requests only JSON containing rules, skill names/descriptions and MCP names. Only known rule tokens, exact skill name/description pairs and the fixture MCP name survive. Root-unique descriptions identify the relative root actually reported; duplicate descriptions show precedence, while missing-description and oversized names show listing, never an inferred rejection reason. Rule order is the order reported by the agent.

The harness then rewrites one `measure-sentinel` description and asks for its description in the same session. Only the new description establishes `openSessionSeesChange: yes`; the exact old description establishes `no`; anything else is `unknown`. Catalogue refresh support and skill toggles remain unmeasured. The third prompt is reserved exclusively for one repeat of a malformed first answer, after the refresh question. The new sentinel is admitted to that repeat only after the harness wrote it. Malformed refresh JSON records `could-not-ask` without retry. Every prompt has a 90-second deadline; a timeout records `could-not-ask: prompt timed out` without retry. Earlier sanitized facts may survive a later refusal, but its raw answer is empty.

The generic ACP driver sends integer `protocolVersion: 1`, empty client capabilities and client information, then `session/new` with an absolute fixture cwd and no MCP servers. ACP has no `initialized` notification. Requests and captured responses stay newline-delimited JSON. An initialize error stops the handshake and records `no-session`; a session error also records `no-session`. Only a request timeout records no answer; a failed launch has its own reason. A session timeout retains an earlier initialize answer.

`facts.signedOutCatalogue` records `initializeAnswered`, `sessionNewAnswered`, `signInMethodCount` (only the length of `authMethods`), and numeric `initializeErrorCode` / `sessionNewErrorCode` when present. It never stores sign-in method names, descriptions, session identifiers or error messages. Catalogue status stays `unknown`, including when a session succeeds.

Run the regression suite explicitly (it is a manual harness, outside the gate-test glob):

```sh
node --test script/measure/library.test.mjs
```

The subprocess tests use the scripted ACP fixture with strict v1 validation and request capture added to a disposable copy. They cover success, sign-in refusal, initialize refusal, timeout preservation and launch failure without running a vendor agent. The mutation proof restored a byte-exact backup of the original probe: the session-success test failed with `could-not-ask` instead of `asked` (exit 1). Restoring the fixed backup was checked byte-for-byte and the focused suite passed.

Ask tests use disposable copies of the ACP and Codex scripted peers. They exercise fixed questions, a single session, JSON retry/refusal, refresh, timeout, fabricated sentinels and a synthetic environment value echoed on both protocol and stderr. The result/capture checks retain neither value. The profile-selection test enumerates every registered agent and the isolation selection sites, and the sandbox profile source is pinned unchanged. Mutation proofs remove the prompt cap, environment-name guard and profile guards one at a time; each must fail its focused test, with the original restored byte-for-byte before the suite is run again. No real agent receives a model prompt in these proofs.

Bridge regressions resolve and stage disposable copies of the scripted ACP peer, then launch them under `keychain-read-only`. They check both executable environment variables, the Claude marker, missing/unsafe bridge refusals and zero prompts. An import-only check loads both real bundled bridge modules and their staged dependency trees under the same profile without starting a session or running a vendor CLI. Request-failure regressions exercise initialize, session and prompt errors, validate the persisted stage/error class, and prove that synthetic raw error details survive in neither captures nor result files. `probeAcpHandshake` is a diagnostic export that shares ask startup and its error reducer, sends no MCP servers, and stops before any model prompt; it must be used through `run` with a preflighted fixture.

The agent-request regressions run a disposable copy of the scripted ACP peer that logs every message the client writes. Its permission tests offer every option kind and none, and include a peer that, like Gemini, asks again when it is answered with an error: in every case the turn ends only after a valid refusal, only `reject_once` or `cancelled` is ever answered, and no tool call proceeds. A small scripted app-server peer proves the Codex driver still answers a request with `-32601`. A peer that talks, asks and then goes quiet carries a canary in every text, identifier, path and tool-name field it sends: the timeout result holds only the counts, and no canary survives in the result, the persisted file or the captures. The cleanup regressions run the command itself from a staged copy of the harness against a sandboxed scripted agent that leaves a directory nothing can empty: the result is written and `could-not-ask` printed, stderr holds the single `cleanup incomplete` line, and the exit code is 3. Separate tests prove a helper that outlives its agent is gone before the model, ACP-discovery or Codex-discovery driver returns. The Cursor regressions stage a launcher-plus-versions layout like Cursor's: discovery and the captured `--version` agree on the calendar-and-commit version, and one test pins that the same layout under a credential root is refused by the unchanged profile and by that one denial alone. The staged-copy regressions put that layout under a stand-in home's `.local/share`, where the same launcher run in place is refused under the very profile that runs its copy. They check that only the one folder is copied (an older version, a file next to the `versions` folder and an unrelated app's data are planted beside it and found nowhere in the fixture), that file modes are kept and a read-only folder cannot stop the removal, that a link pointing outside the folder is refused four ways (one of them only the operating system's resolution catches) and a link inside is kept, that a folder without the launcher, runtime and bundle, a named pipe, or a folder that holds the home is refused, that a refused copy is not replaced by an in-place launch (and that the command then records `could-not-ask: cannot isolate`), that a second copy at the same place is refused and leaves the first alone, that no other agent or layout is staged and that a copy and an install run in place are found side by side, that the ask path's bridge is handed the copy and the copy runs under `keychain-read-only`, and, running the command itself, that the copy is gone with the fixture and the written result carries its numbers.

Mutation proofs for this change, each file restored byte-for-byte and checked by hash before the suite ran again: answering every request with `-32601` again fails all four permission tests (the turn ends `could-not-ask: prompt timed out`); putting back the bare `rm` in `main()` fails the command-level cleanup test with the old `measurement refused` text and exit 1; putting back the old stop logic (SIGTERM, then wait for the direct child only) fails the helper tests; and each of the three places that check the activity vocabulary, and the version format, fails a test when removed on its own. A scripted battery of twenty small mutations (an uncapped flood, a window that is not reset, an update kind kept under the agent's own name, `reject_always` accepted, an unreduced error code or full path in the cleanup line, a driver that does not drain its group, and others) is killed by at least one test each. No real agent received a model prompt in these proofs.

Mutation proofs for the staged copy, each file restored byte-for-byte and checked by hash before the suite ran again, and the tree checked clean by git after the last: one extra rule in `sandboxProfileText` fails the pinned-hash test; removing the outside-link check fails the four link cases and the no-fallback test; swapping the native `realpathSync` for Node's own fails the one link case that spells a path inside the folder and ends outside it, which exists for exactly that; and each of these fails the test written for it: copying the parent `versions` folder as well, launching the install instead of the copy (in the chosen path, and in the probe), launching in place when the copy is refused, removing the layout check, staging every agent that has a versions folder, keeping a folder's exact source mode (a read-only folder then cannot be removed), skipping a pipe instead of refusing it, refusing every link, refusing a link to nothing, removing the real-home guard, and allowing the real folder to be read. Making the copy beside the fixture, or not removing the fixture, fails the command-level test; not attaching the numbers, admitting a negative number, a fraction, a fourth name or any agent, and recording zeros for a run in place each fail the record's tests. Twenty-six small mutations, all killed and none left in the tree: sixteen for the copy, eight for the record, one for a refused copy seen from the command and one for a second copy made over the first. The one for the refused copy survived the first version of its test, because under a credential root a launch in place is refused anyway and the result is the same either way; the install now sits where a launch in place would work. No real agent received a prompt in these proofs.

`docs/verification/library-measurements/README.md` maps each result JSON cell to its fact: `facts.rulesFiles` → rules read/load order; `facts.catalogue` plus `facts.reportsCatalogue` → fixture reach/catalogue reporting; `facts.precedence` → duplicate-name precedence; `facts.rejections` plus `facts.reportsRejections` → acceptance/reason and rejection reporting; `facts.skillRoots` → concrete tier C root paths; `facts.refresh.catalogueRefresh`, `facts.refresh.skillToggle`, and `facts.refresh.openSessionSeesChange` → refresh behavior; `facts.mcp` → config recognition and connection status; `facts.signedOutCatalogue` → available/empty/unknown while signed out. Each cell links its exact `<agent>-<version>.json` result or gives its `could-not-ask` reason.
